# 接诊记录与超星登录接入

本功能按 Supabase Auth 的学生账号保存接诊记录。问诊、四诊、辅助检查、诊断、处置及体格检查快照和提交记录保存在同一条接诊记录中；同一接诊 ID 重复保存会更新该记录。

草稿在修改后约800毫秒自动同步，提交和结束接诊立即触发同步。尚未收到云端确认的记录会暂存在当前浏览器的待同步队列中，按已登录学生的 Auth UUID 分开，不保存登录令牌。刷新或退出后，同一学生重新登录会重试；其他账号不会上传或显示这些待传内容。成功同步后删除相应缓存。浏览器禁用存储、清理站点数据或达到容量上限时无法保证本机恢复，应等待界面显示“已保存”后离开；仍待同步时提供离开页面保护。云数据库仍是正式记录来源。

## 部署配置

1. 在 Supabase 项目中执行 `supabase/migrations/20261113140000_encounter_records.sql`。该迁移创建记录表、更新时间触发器和学生本人读写的 RLS 策略。
2. 在应用服务端配置以下环境变量，重启服务：

   ```dotenv
   SUPABASE_URL=https://你的项目.supabase.co
   SUPABASE_PUBLISHABLE_KEY=你的公开publishable_key
   # 使用旧版公开anon JWT时，留空上项并填写下项。
   SUPABASE_ANON_KEY=
   ```

3. 接诊记录的读写只使用公开 key 和学生会话。`/api/records-config` 返回 `{url,publishableKey}`，平台多租户配置下可附公开的 `tenantId`；不会返回服务器管理密钥。把 secret key 或 `service_role` JWT 误填到公开 key 位置时返回 503。

已有 `SUPABASE_*` 配置优先且必须完整，不能与另一项目的 `CODER_SUPABASE_*` 配置混搭。未设置旧配置时可直接使用平台注入的 `CODER_SUPABASE_URL`、`CODER_SUPABASE_ANON_KEY` 和可选的 `CODER_SUPABASE_TENANT_ID`；客户端和服务端相应携带 `X-Instance-ID`。

Supabase 区分应用的公开 API key 和用户的 Auth access token；公开 key 不能替代学生登录。带用户会话的数据库请求仍受 RLS 约束。[Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)

## 超星登录：独立认证中心与项目内桥接

超星认证中心返回的 `{uid,name,fid,roles,...}` 不是 Supabase session，不能直接作为 Bearer token，也不能直接传给 Supabase `setSession`。

本项目沿用独立认证中心 `https://sdtqvk3ybm.coze.site`，由本项目服务端验票并建立医院项目自己的 Supabase 会话。学校已登记的超星应用继续由认证中心维护，本项目不收集超星账号密码。

首页可公开浏览，点击“开始实训”时必须先完成学生登录，成功后进入 `/training`。直接打开 `/training` 也会检查会话，未登录或会话失效时仅显示登录入口；恢复已有会话期间暂停进入实训。认证配置缺失时提示联系管理员，不放行案例。

服务端环境变量（真实值只填服务器环境，不要填前端或 public）：

```dotenv
SSO_CENTER_URL=https://sdtqvk3ybm.coze.site
APP_PUBLIC_URL=https://你的医院项目域名
SSO_SHARED_SECRET=
SSO_SESSION_SECRET=
SSO_IDENTITY_SECRET=
SUPABASE_SERVICE_ROLE_KEY=
```

- `APP_PUBLIC_URL` 是浏览器访问的本站完整 origin。生产使用 HTTPS；本机当前使用 `http://localhost:5174`。必须与实际浏览器地址的协议、主机及端口一致，不能把 localhost 与 127.0.0.1 混用，否则回跳收不到原登录 Cookie。若采用用户提供的内部访问地址，则设置为 `https://g7wmptzcb3.coze.site`，同时确认该地址确实绑定本医院项目的云库。
- `SSO_SHARED_SECRET` 必须与旧认证中心的验票共享凭据一致；由认证中心管理员在服务端配置，不能放到浏览器。
- `SSO_SESSION_SECRET` 至少 32 个字符，用于加密短期登录上下文和会话交接 Cookie。
- `SSO_IDENTITY_SECRET` 为独立的至少 32 字符的稳定身份映射密钥。首次由平台生成并安全保管，所有实例和后续部署必须保持一致；更换它或认证中心的 origin 会改变超星身份对应的内部邮箱，必须先做账号映射迁移。不要用可轮换的 Cookie 密钥替代它。
- `SUPABASE_SERVICE_ROLE_KEY` 仅由新增的登录桥接使用，用于创建/查找受控学生用户并签发本项目会话。它必须与公开配置属于同一个医院 Supabase 项目；普通接诊记录接口继续用学生自己的 token 和 RLS，不用该管理密钥读写学生记录。

此桥接使用 Supabase 官方支持的服务端 [createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser)、[generateLink](https://supabase.com/docs/reference/javascript/auth-admin-generatelink) 和 [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp) 流程；不新增密码登录表单，也不手工伪造 Supabase JWT。

服务端实际流程：

1. 首页与实训页的“超星登录”进入本站 `/api/auth/chaoxing?next=...`。服务端生成加密、HttpOnly、SameSite=Lax 的短期 state Cookie，再跳转认证中心 `/api/auth/chaoxing?return_to=...`。
2. 认证中心回跳本站 `/api/auth/chaoxing/callback?state=...&ticket=...`。本站先检查 state，再在服务端 `POST /api/sso/verify`，JSON 仅发送 `{ticket,secret}`，票据过期与否以中心验票结果为准。
3. 用已验证的中心 origin 和稳定 uid（必要时使用 openid）生成带专用 HMAC 的内部邮箱。新用户通过 Admin API 建立真实 Auth 用户并写入只有服务端能修改的 `app_metadata.hospital_sso`。已有用户必须匹配这份可信映射，否则拒绝登录，不接管普通邮箱账户。
4. 服务端生成并验证一次性 magic link token，取得真实 `access_token`、`refresh_token`。管理密钥、内部 link 和票据均不回传到登录 URL。
5. 服务端把会话放入 90 秒有效的加密 HttpOnly 交接 Cookie，仅跳到 `/auth/chaoxing/callback`。前端同源 `POST /api/auth/chaoxing/session` 取出会话，服务端清 Cookie；客户端防止 StrictMode 重复交接。
6. 前端调用 `setStudentSession`，并用 Supabase `getUser()` 验证返回身份。登录后恢复开始登录前的本站页面；刷新会恢复 Supabase 会话。退出时先清除本站会话，再跳旧中心 `/logout?return_to=...` 联动退出。

   ```ts
   import { setStudentSession } from '@/records/studentSession'

   // 两个值由服务端桥接返回，不能用超星uid或一次性ticket替代。
   await setStudentSession({ access_token, refresh_token })
   ```

接诊记录 API 每次都会向 Supabase `/auth/v1/user` 验证 Bearer，采用其返回的用户 UUID 作为 `student_id`。不会从前端的 `studentId`、超星 uid、JWT 本地解码结果或 localStorage 中推断登录身份。Auth 用户查询会真实访问认证服务，适合用作授权判断。[Supabase getUser](https://supabase.com/docs/reference/javascript/auth-getuser)

平台网关将 Authorization 改名时，服务端优先读取 `x-sandbox-authorization`；只有该头缺失时才使用本地标准 Authorization。无效的平台头不会回退到另一个令牌。

登录配置不全时，按钮明确提示“尚未配置”，不会建立假用户、共享学生账号或绕过记录权限。旧中心只返回身份，单独填 `SSO_CENTER_URL` 并不能建立 Supabase 会话；桥接管理配置和公开云库配置都需要就绪。

## 接口

- `GET /api/auth/chaoxing/config`：安全的登录可用状态，不返回任何密钥。
- `GET /api/auth/chaoxing?next=/training`：发起旧认证中心登录。
- `GET /api/auth/chaoxing/callback`：服务端收票、验 state、验票和桥接。
- `POST /api/auth/chaoxing/session`：校验同源 Origin 后交接会话并清除短期 Cookie。
- `GET /api/auth/chaoxing/logout?next=/`：安全同站回跳的中心联动退出。

- `GET /api/records-config`：读取安全的云端公开配置；未配置返回 503。
- `GET /api/encounters?offset=0`：携带 `Authorization: Bearer <Supabase access_token>`，返回 `{records,hasMore}`，每页最多 50 条摘要。
- `GET /api/encounters?id=<UUID>`：返回本人记录的完整 `{record}`，包含快照与提交；不存在或不是本人所有的记录返回 404。
- `PUT /api/encounters`：携带同一 Bearer 和 JSON 接诊记录，按记录 ID upsert，返回云端确认的 `{record}`。请求体最大 512KB。

记录使用 camelCase：`id`、`caseId`、`patient`、`startedAt`、`endedAt`、`status`、`snapshot`、`submissions`；返回时可额外包含数据库生成的 `updatedAt`。摘要包含相同元数据，不包含 `snapshot`、`submissions` 或 `student_id`。

服务端将已验证的用户 UUID 写入 `student_id`，并以学生本人 Bearer 和公开 key 访问 PostgREST。RLS 对 select、insert、update 分别检查 `auth.uid() = student_id`，更新时还校验更新后的归属；没有教师或其他学生的读取权限，也未开放删除接口。

无登录返回 401，跨学生修改返回 403，无云配置或未迁移返回 503，上游故障返回安全错误。未收到保存成功响应时，界面应保持未保存状态，不得显示为已同步。

## 验证范围

`pnpm exec vitest run tests/encounterRecordsApi.test.ts` 使用本地模拟的 Supabase Auth/PostgREST HTTP 服务验证登录校验、本人读写、跨账号拒绝、重复保存、分页、请求格式和大小限制，以及公开配置过滤。该测试同时覆盖 Express 与 Next 两种入口。

新增 SSO API/桥接单元测试以本地模拟认证中心和 Supabase 验证 state、票据、身份映射、会话交接、错误脱敏与回跳限制；浏览器登录测试拦截认证响应，验证界面、交接去重、刷新恢复及退出，不能代替真实超星登录。

当前本机缺少医院项目真实 Supabase 管理配置，未完成真实超星到医院云会话、两个真实学生隔离和跨设备保存读取验收。平台中配置上述环境并重启后，需要用两名真实学生完成这些检查；不要把本地模拟结果当作已上线登录成功。
